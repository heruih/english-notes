# 决策记录（为什么是这样）

> 目的：**防止以后有人（包括 AI、包括未来的你）重提已经否过的方案。**
> 每条写三件事：当时为什么这么选、代价是什么、什么情况下值得重新考虑。
> 不是历史文档——是**挡箭牌**。

---

## D1. 单文件 HTML，不用框架

**决策**：一个 `.html` 文件装下所有 CSS/JS，无构建、无依赖、无 CDN。

**理由**：手机离线能直接打开；换设备只要传一个文件；没有构建链就没有"构建失败"这一类问题。

**代价**：405 KB、442 个函数全在一个文件里；每次改动都要 AI 重读全文，token 成本高；多人交接必然混乱（已经发生过）。

**什么时候重议**：拆成 `src/js/*.js` + `build.py`，产物仍是单文件——**这不叫推翻 D1，叫补上它的缺口。**真正推翻 D1（改成多文件部署）需要理由：出现第二个使用者、需要热更新。

---

## D2. 不引入框架（Vue / React / Next.js）

**决策**：原生 JS + `contenteditable`。

**理由**：框架带来打包体积、构建链、版本升级、hydration 问题；这个 App 的交互核心是"编辑一段富文本 + 弹一个词卡"，原生够用。

**代价**：状态变更要手动调 `render()`；组件复用靠函数拼接。

**什么时候重议**：**基本不会。**反面教材就在旁边——Trinity 用 Next.js 做私人工具，框架包 500 KB，功能没比它多。

---

## D3. 数据只在浏览器本地（localStorage）

**决策**：没有后端、没有账号、没有数据库。主键 `english-notes-app-v1`。

**理由**：零成本、零延迟、零隐私风险；一个人用不需要服务端。

**代价**：换设备要手动搬；清浏览器数据就没了（所以有导出备份和同步码）。

**什么时候重议**：真出现"多人使用"或"跨设备实时"需求时。**目前明确不做**（见需求 D-4/5）。

---

## D4. 同步走 Gist / WebDAV + 同步码，不自建后端

**决策**：多设备同步用 GitHub Gist 或 WebDAV，再加一个 `ENSYNC1:` 的 base64 同步码做"无网络也能搬"。

**理由**：不自建服务器、不付费、不维护。

**代价**：配置麻烦（token、地址、ID）；CORS 与 Gist 超时踩过多次；token 明文存本地。

**什么时候重议**：如果同步连续三次以上失败，或者用户开始抱怨配置——那时再考虑"一键导入导出文件"替代。

---

## D5. 复习用 Leitner 分箱，不用 SM-2/FSRS

**决策**：`srs.box` 1–6，间隔 `[0,0,1,3,7,15,30]` 天，评分三档（忘了/难/记住了）。

**理由**：三个按钮能解释清楚；算法可预测、可调试；不需要"难度系数"这类黑箱参数。

**代价**：不如 FSRS 精准。

**什么时候重议**：自用 30 天后如果发现"该复习的没出现/不该出现的总出现"，再考虑。

---

## D6. AI 只补例句，绝不覆盖释义与标签

**决策**：`definition` / `phonetic` / `tags` 由用户手填；AI 生成的 `examples` 只追加、去重、不覆盖。

**理由**：用户主权——释义是他自己的理解，AI 一覆盖就变成"背 AI 的话"。

**代价**：录入比全自动慢。

**什么时候重议**：**不重议。**这是产品价值观，不是技术选择。

---

## D7. 词典页复刻欧路格式，不接词典 API

**决策**：词典页的数据由已配置的 AI 按欧路结构生成 JSON。

**理由**：有道 jsonapi 带 Origin 就 403；dictionaryapi.dev 在 `file://` 下被 CORS 拦；datamuse 无 CORS 头。**离线 + 单文件**和"直连词典 API"天然冲突。

**代价**：释义与真实词典有出入；词条质量取决于模型。

**什么时候重议**：出现愿意付费的词典 API，且能解决 CORS/离线问题。

---

## D8. 发音：有道真人音源 + 系统 TTS

**原决定（历史）**：单词走有道 `dictvoice`；句子和中文走浏览器 `speechSynthesis`（女声优先，rate 0.95）。

**2026-11-11 调整**：英语优先选同口音的本地增强/优质音色，单词、短语与句子尽量统一。普通美式英语单词在缺少高质量音色且联网时沿用有道，加载失败回退系统音色。以整句和原标点朗读，具体听感取决于设备提供的音色。需要回滚时可使用 `7414ed9` 的构建。

**理由**：试过模仿豆包"小姐姐"音色，多版合成后**固定录音无法朗读任意句子**，只能回退。豆包音色是字节私有的，网页做不到。

**代价**：音色不统一（单词一个声音、句子另一个声音）。

**什么时候重议**：字节开放 TTS 公开接口，或愿意接火山引擎（要付费、要后端签名）。

## D9. 什么时候必须拆模块（触发条件）

**默认不拆。但只要命中下面任一条，就必须先拆再改。**
判断依据是"改动的影响面"，不是"感觉代码乱了"。

### L1 / L2 —— 直接改，不用拆

- L1：文案、颜色、间距、图标、按钮位置
- L2：单个函数内的小改（排序规则、按钮出现条件、快捷键）

### L3 —— 建议拆（命中就先停下来判断一次）

- [ ] 要加**设置项**或**新状态**
- [ ] 要动 `words` / `notes` 的**字段**（先看 `docs/数据模型.md` 的六条铁律）
- [ ] **同一段逻辑要在两个以上地方同时改**
- [ ] 单次改动需要读**超过一屏（约 150 行）**代码

### L4 —— 必须先拆，拆完再动

- [ ] 改**同步**（Gist / WebDAV / 同步码 `ENSYNC1:` / 墓碑合并）
- [ ] **页面重排**或视图切换逻辑改动
- [ ] **抽公共组件**（一处改动会影响 3 个以上视图）
- [ ] 命中《项目通用准则》5.3 红线第 1 条（单文件 > 2000 行）

> 注：当前文件 **7,911 行**，早已越过 2000 行红线。这条红线对 L1/L2 **豁免**（否则什么都改不了），对 L3/L4 **生效**。

## D10. 复习页不提供"新建标亮"

**决策**：复习页只**显示**标亮，不提供划词标亮能力。

**理由**：①卡片点击=翻面，划词手势会打架；②复习是回忆场景，不是编辑场景；③要改标亮就去词卡，那里功能齐全。

**什么时候重议**：如果连续两周发现自己每次复习都想标亮某句——那说明该改的是"进入词卡的路径"，不是"加一套新交互"。



1. **推翻一条决策，必须写清三件事**：新证据是什么、代价能否接受、什么时候能回滚。
2. **"看起来更专业"不是理由**。上一个"更专业"的选择（Next.js）让 Trinity 付出了 500 KB 框架的代价。
3. **凡是改数据结构、改同步、改 AI 行为的决策，先看 `docs/数据模型.md` 的兼容铁律。**

## D11. 源码模块化，交付仍保持单文件（2026-11-10 用户决定）

**决定**：把原来的单文件源码拆成 `src/index.html`、`src/style.css` 和 `src/js/*.js`，由 `scripts/build.mjs` 拼回 `dist/英语学习笔记.html`。不改变页面、功能、localStorage key 或数据字段。

**理由**：原文件约 648 KB，继续整文件维护会让交接、审查和小改动都重复读取大量上下文。单文件仍作为手机离线交付物保留。

**验收**：构建产物与拆分前文件逐字节一致，现有页面和数据行为沿用原代码。

**回滚**：回到拆分前的 Git 检查点，或直接使用该检查点生成的单文件产物。

## D12. 今日复习在同一设备续接（2026-11-11）

**决定**：给当前到期轮次单独保存有序词条 ID 和开轮时的复习次数。重新进入时从仍未评分的词条继续。评分持久化失败时回滚内存中的单词进度。

**理由**：手机重新打开文件时旧版按到期词重排，丢失本轮位置。用已落盘的复习次数推导下一张卡，可避免评分和轮次进度分两次写入。

**影响**：新增独立本机 key，既有词条字段及备份、同步协议沿用。未完成的轮次保留，完成后再次进入按当前到期词开新轮次。

**回滚**：重新使用 `613bd2a` 的单文件或此前的 Sitecase 文件。旧版忽略新增的轮次存储项，仍读取已保存的词条评分。

## D13. Sitecase 录音和截图导入（2026-11-11）

**决定**：iOS 跟读只启动录音，沿用回听和节奏/音量评分。对话保留系统语音识别，权限被拒时回到输入框供键盘听写。相机图标绑定原生图片文件控件。

**回滚**：使用 `7414ed9` 的构建，沿用原来的笔记、标亮和录音数据。

## D15. DeepSeek 默认、GPT 备用的 AI 对话（2026-11-12）

**决定**：AI 自动模式默认使用 DeepSeek `deepseek-flash`，OpenAI GPT 作为可切换备用。ChatGPT 往返保留为手动模式。每次对话生成一个场景、1—2 个来回，并在唯一的学习者句子中指定目标词。

**理由**：用户希望点击后直接进入场景练习，同时保留 ChatGPT Plus 的自然对话入口。DeepSeek 官方当前推荐 `deepseek-flash`，接口兼容 OpenAI Chat Completions。

**影响**：新增独立 `en-ai-providers-v1` 本机 key。两个 API 提供商的 Key 分开保存，不进入备份和公开构建。自动切换到 GPT 需要用户配置 GPT API Key。

**回滚**：设置切换为 ChatGPT 往返，或清空 API 配置。既有单词和 AI 练习记录继续保留。

_最后更新：2026-11-12 · 依据当前源码、DeepSeek 官方文档和用户决定_

## D14. 在线豆包 TTS 2.0（2026-11-11）

**决定**：联网时单词和英文例句优先调用豆包语音合成 2.0，按文本首次播放生成音频，之后从本机缓存播放。API Key、音色、语速和音调放在独立的 `en-tts-v1` key，不进入备份和公开构建。

**理由**：用户已试听并确认豆包音色效果。按需合成只消耗实际听过的文本，避免一次性生成整库音频。

**影响**：需要用户在设置中粘贴豆包 API Key。浏览器直连第三方语音服务，密钥只保存在当前设备。接口失败自动回退到有道或系统朗读。

**回滚**：清空设置中的豆包 API Key，页面自动回到原有朗读路径。

_最后更新：2026-11-11 · 依据当前源码和用户决定_

## D16. 单词学习卡片与截图批量收件箱（2026-11-12）

**决定**：打开词卡默认进入紧凑学习视图，只显示配图、释义、第一条例句和口语入口；其余字段通过“编辑整理”和“更多例句”展开。相册多选截图先进入本机 `en-shot-inbox-v1` 收件箱，OCR 给出候选词条，由用户逐项确认后才写入既有截图 key。

**理由**：单词页优先支持快速复习，批量截图需要保留人工确认，避免 OCR 误匹配污染词库。收件箱只在本机保存，不进入云同步和完整备份。

**影响**：既有词条、截图 key 和字段不变；未确认的收件箱项目在清理浏览器数据后会丢失，需要重新从相册导入。

**回滚**：关闭词卡顶部的紧凑模式，或删除 `en-shot-inbox-v1` 后继续使用原单张截图导入。

_最后更新：2026-11-12 · 依据当前源码和用户决定_

## D17. 豆包 TTS 服务端中转（2026-11-13）

**决定**：保留直连模式，同时增加可选的服务端中转地址。网页发送 `req_params` 到中转 Worker，Worker 使用 Secret 中的豆包 API Key 请求 TTS，再把结果返回网页。中转地址为空时沿用直连路径。

**理由**：Sitecase 和线上页面都出现 `Load failed`，接口预检可达但手机实际请求仍失败。把 Key 和豆包请求移到服务端，减少本地 WebView 网络限制和浏览器请求链路的影响。

**影响**：新增 `relay/doubao-tts-worker.js` 和部署说明。Worker 需要单独部署并配置 `DOUBAO_API_KEY`。未部署中转时，当前线上回退版本继续使用原有行为。

**回滚**：网页设置清空中转地址即可回到直连模式。线上发布仍以 Worker 实际验通为前提。

_最后更新：2026-11-13 · 依据当前源码、豆包接口检查结果和用户决定_
