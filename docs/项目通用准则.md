# 项目通用准则 v1

> 适用于**所有项目**。新项目开工第一步：把本文件复制成该项目根目录的 `AGENTS.md`，把下面每一节的「填空」写掉。
> 来源：2026-11 堡垒项目的实际教训（3 个 AI 改同一个仓库、文档互相矛盾、旧状态被当现状）。每条都是踩过才写下来的。

---

## 零、一句话总则

> **先定蓝图，再划边界，然后才让 AI 动手；每一次改动和每一个决定都要留下能被人读懂的痕迹。**

没有蓝图的代码是猜测，没有边界的协作是事故，没有记录的改动等于没发生。

---

## 一、第一阶段：先定蓝图（没有蓝图不许写代码）

**蓝图是产品定义，不是讨论稿。** 它必须回答：

| 内容 | 最低要求 | 填空 |
|---|---|---|
| 目标 | 用一句话说清"谁在什么场景下用它解决什么" | |
| 非目标 | **明确写"不做什么"**——这一栏比目标更值钱 | |
| 现实约束 | 时间、设备、网络、体力、预算 | |
| 功能清单 | 按模块列，每个模块写"必须支持" | |
| 数据模型 | 实体、字段、关系、删除/归档语义 | |
| 验收标准 | 编号 A01、A02…，每条必须能判"过/没过" | |
| 依赖与风险 | 哪些能力取决于外部条件（网络、账号、平台） | |

**规矩**

1. 蓝图进仓库：`docs/blueprint/`，**只读**，改动要单独一次提交并说明原因。
2. 蓝图里区分三种标记：`【已确认】`（用户说的）、`【建议默认】`（可调）、`【待验证】`（取决于环境）。
3. 蓝图没写的功能**不做**；想加先改蓝图，再改代码——顺序不能反。
4. 与实现不一致时：先查 `docs/decisions.md` 有没有"有意偏离"的记录；**没有记录的才算缺口**。这条能防止后来者把决策当 bug 修。

---

## 二、第二阶段：划主线（哪里能动、哪里不能动）

开工前必须把仓库里的东西分成三类，写进 `docs/decisions.md` 的「边界清单」：

| 区域 | 含义 | 例子 | 谁可以动 |
|---|---|---|---|
| **只读区** | 动了就是事故 | 蓝图、构建产物（`dist/`）、迁移函数、已发布的协议 | 谁都不能直接动；要改先立新版本 |
| **可改区** | 日常开发区 | `src/`、`tests/`、`docs/`（除蓝图） | 认领后自由改 |
| **需批准区** | 影响兼容性/数据 | 数据结构版本、认证方式、部署配置、删除语义 | 必须先说清楚影响面，用户点头 |

**判定标准**：改「需批准区」任何一项，必须同时做三件事——
1. 升数据版本或写迁移；
2. 在 `decisions.md` 写明"为什么改、代价是什么、怎么回滚"；
3. 告诉用户这次改动的**不可逆部分**在哪里。

**填空：本项目的三张清单**

```
只读区：
需批准区：
可改区：
```

## 三、第三阶段：AI 之间的交接与修改

### 3.1 进门的固定动作

**换人（或换 AI）第一句话不是"继续"，而是先读四样**：

```
1. AGENTS.md        —— 规矩
2. docs/HANDOFF.md  —— 现在做到哪、下一步、已知问题
3. docs/backlog.md  —— 还剩什么、优先级、验收标准
4. git log -5       —— 最近发生了什么
```

读完先**用一句话复述"我要改什么、改哪个文件"**，再动手。

### 3.2 交接传「上下文」，不传「结果」

给下一个 AI 的东西应该是：**仓库 + 规矩 + 状态**。
不是：网址、截图、压缩包、聊天记录。

理由：结果会过期，上下文不会。把仓库和规矩交出，对方能自己算出结果。

### 3.3 同一时间只有一个 AI 改文件

- 动手前声明：**"我要动 `src/xxx.js`"**，另一边避开。
- 同仓库只有一个工作副本 = 一个 `HEAD`，两个 AI 同时改就是互相覆盖。
- 提交信息加前缀区分来源（见 3.4）。

### 3.4 提交与身份

| 前缀 | 谁 |
|---|---|
| `[dsh]` | DeepSeek Harness 的 AI |
| `[codex]` | Codex / ChatGPT 侧 |
| `[user]` | 用户手改 |

**为什么必须加**：同一台机器上所有 AI 的 git 作者往往是同一个本地身份，`git log` 里分不出来。

提交信息写「做了什么」，不写 `update`。**一次提交只含本任务的改动。**

### 3.5 冲突预防

- 一次只推进**一个**主项目，其他项目冻结或只读。
- 新功能必须写进 `backlog.md` 再动手，避免"顺手改"。
- 看到别人没提交的改动 → 不覆盖、不 stash、先问。

## 四、第四阶段：维护与优化必须留痕

**核心原则：不记录 = 没发生。** 下次会被重做、改回、或当成 bug 修掉。

| 什么时候 | 记在哪 | 记什么 |
|---|---|---|
| 每次改动 | `DEVLOG` / `CHANGELOG` 一行 | 做了什么 / 怎么验的 / 下一步 |
| 每个技术选择 | `decisions.md` 一条 | 背景 / 决定 / 理由 / 代价 / 何时重新考虑 |
| 每个阶段 | `HANDOFF.md` 顶部 | 做到哪、未做、下一步、对应提交号 |
| 每次优化 | `backlog.md` 对应条目 | 优化前后差异 + 验收依据 |
| 每次踩坑 | `decisions.md` 或文档备注 | 现象、根因、怎么绕过去 |

**五份文件各管一件事，不许互相替代**：

```
AGENTS.md    规矩：怎么干活
HANDOFF.md   状态：干到哪了（最新在最上面）
backlog.md   待办：还剩什么（唯一真源）
decisions.md 理由：为什么这么干（含不可改清单）
blueprint/   定义：要做什么（只读）
```

**文档两条铁律**

1. **过期不删，标「历史」**——历史上踩过的坑比结论值钱。
2. **一个事实只有一个出处**：状态看 HANDOFF，待办看 backlog，理由看 decisions。同一件事写在两处，迟早互相矛盾。

## 五、新项目 30 分钟启动清单

```
□ git init
□ 建五个文件：AGENTS.md / docs/HANDOFF.md / docs/backlog.md / docs/decisions.md / docs/blueprint/
□ 写蓝图 v0.1（哪怕一页：目标、非目标、约束、功能清单、验收 A01–A05）
□ 划三张清单（只读区 / 需批准区 / 可改区）
□ 写第一条决定（D-01：技术形态为什么这么选）
□ 写第一条待办（B-01：第一个可验收的功能）
□ commit：[user] chore: 建立项目骨架与蓝图 v0.1
```

**判定"能开工"的标准**：说得出"这次改哪个文件、改完怎么验"。说不出来，先回去写蓝图或测试清单。

## 六、反模式（都是真踩过的）

| 反模式 | 后果 |
|---|---|
| 先写代码，规格后补 | 功能越加越多，没人知道边界在哪 |
| 同一件事有两份待办 | 一份说做完、一份说没做，AI 会重做 |
| 文档不标历史 | 旧报告被当成现状，去"修"已经修好的东西 |
| 所有 AI 共用一个提交身份 | 出问题分不清是谁改的 |
| 单文件巨兽（40 万字符） | 每改一个按钮都要重读全文件，成本高一个数量级 |
| "功能我全都要" | 维护成本不是线性涨，是"每个功能带一套状态机" |
| 用规划代替动手 | 第三份规划通常会变成第三份负担 |
| 用截图代替验收 | 贵，且抓不住真问题；写"怎么复现"才有效 |

## 七、已经跑通的样例

堡垒项目（`Documents\Codex\...\work\fortress`）是本准则的第一次完整落地：

- 蓝图：`docs/blueprint/v1-full.md`（只读）
- 边界：`docs/decisions.md` D-09「不可改清单」
- 交接：`docs/HANDOFF.md`（按日期倒序）
- 待办：`docs/backlog.md`（B-01…B-20，带状态与负责人）
- 验收：`docs/acceptance-results.md`（A01–A25 逐条给依据）

新项目可以直接照这套结构复制。
